# sync-docs

输出：与一段代码改动对应的文档修改，每处修改都能在 diff 中找到依据；使用说明与参考文档只描述修改后的当前行为。

## 何时使用

- 改完代码后，在汇报任务完成或提交之前，即使用户没有提出，也主动检查文档是否受影响；受影响时询问用户是否同步。
- 用户说“文档要不要改”“把文档同步一下”。
- 用户指出某处文档和实际行为不符。

## 何时不用

- 写发布说明或 CHANGELOG → release-notes。
- 从零写一份新文档。

## 先取事实

1. 改动范围：用户指定了提交范围 → `git diff <范围>`；未指定 → 工作区中还没有提交的改动（`git diff HEAD`，以及 `git status --porcelain` 中 `??` 的文件）；工作区也没有改动 → 请用户指定提交范围。
2. 改动只有下列内容时，回复“本次改动不影响文档”并列出判断依据，然后结束：
   - 格式化、空白、注释；
   - 只改测试；
   - 不出现在任何文档中的内部重命名；
   - 不改变行为的依赖版本升级。
3. 从 diff 提取会出现在文档里的标识：环境变量、配置键、命令与参数、接口路径与字段、默认值与单位、端口、文件路径、运行环境要求、支持的平台。
4. 按改动类型确定要核对的文档：

| 改了什么 | 核对 |
| --- | --- |
| 命令、参数、接口、错误码 | 使用说明、接口参考、示例代码 |
| 环境变量、默认配置、初始化步骤 | 快速开始、部署说明、配置表 |
| 数据格式、存储位置、数据库结构 | 升级说明、备份与恢复 |
| 平台、运行环境、安装方式 | 安装要求、下载说明 |
| 构建、测试、代码生成命令 | 贡献指南、开发说明 |
| 用户可见行为 | 使用说明中对应功能的段落 |

5. 在文档中定位：对每个标识运行 `git grep -n --untracked -F -e "<标识>" -- '*.md' '*.mdx' '*.rst'`（`.github/` 等隐藏目录与未跟踪的文件也会搜到）。默认值、端口、版本号这类数值，搜 diff 中被替换掉的旧值及其换算写法：旧值 3600 秒 → 搜 `3600`、`1 小时`、`60 分钟`、`1 hour`。
6. 新值从源头核对：默认值读源码常量或 schema；接口读接口定义或路由；命令读 `--help` 输出或 package.json scripts。文档由命令生成时（如 `npm run docs`），先读命令内容：只在本地生成文件的 → 运行，不手改生成物；会发布、部署或推送的 → 不运行，列为需要人工处理。
7. 按工作区的改动同步时，修改之前先询问：列出这些改动的文件、受影响的文档和各处要改的内容，问用户是否同步；得到回答前不改文件，也不运行第 6 步中生成文档的命令。没有受影响的文档时不询问，按第 2 步回复。

## 修改规则

- 使用说明、参考文档、README 只描述当前行为。所修改的句子里，描述产品随版本变化的说法改为直接陈述：
  - “目前支持 X”“现在可以 X”“新增的 X” → “支持 X”“可以 X”“X”；
  - “以前是 A，已改为 B”“不再使用 A” → 只写 B；
  - “即将支持 X”“暂时不支持 X” → 不写对未来的承诺，需要时写“不支持 X”；
  - 指代操作或界面的词照常使用，例如“当前目录”“新建项目”“把端口改为 9090”。
- 升级与迁移说明（升级指南、迁移文档、文档中的“升级”一节）写从哪个版本升级到哪个版本、按顺序要做的操作，用版本号指明前后，不用“新版”“旧版”。
- 只改受影响的句子，不调整段落顺序和文档结构。
- 新增内容：一两句 → 写进相关段落；一段以上且项目有专门的文档（`docs/`、`USAGE.md`）→ 写进专门文档，README 只加一句和链接。
- 配置表、参数表新增一项：按表格已有的列填写，放在相关项旁边。
- 同一文档有多种语言版本（`README.md` 与 `README.zh-CN.md` 等）→ 每个版本都改。
- 为什么改、改之前是什么，不写进使用说明和参考文档；变更历史由 CHANGELOG 记录。
- 不修改：CHANGELOG.md、已发布的发布说明、ADR 等决策记录（它们记录的是当时的事实）。
- 代码里确认不了的信息（新配置项的确切语义、取值范围、适用场景）只写已确认的部分，其余列为需要人工确认。

## 检查

1. package.json scripts、Makefile、`.github/workflows/` 中有 `markdownlint`、`lint:md`、`docs` 一类的文档检查命令 → 先读命令内容：只做检查或本地生成的，运行并记录结果；会发布或推送的，不运行。
2. 没有 → 检查修改过的文件里，相对链接和锚点都指向存在的位置。

## 示例

diff：命令行工具 `acme` 的 `src/cli.ts` 新增 `archive` 子命令（`--before <日期>`，默认 30 天前），删除 `--legacy-output` 参数。

搜索 `legacy-output` 命中 `docs/cli.md` 的参数表和一句说明；搜索子命令列表命中 README 的“用法”一节。

`docs/cli.md` 修改前：

```markdown
| `--legacy-output` | 按 1.x 的格式输出 | 关闭 |

目前仍支持 `--legacy-output`，新脚本请不要使用。
```

修改：删除 `--legacy-output` 这一行和那句说明；新增 `archive` 一节：

```markdown
## archive

把指定日期之前的记录移入归档文件。

| 参数 | 说明 | 默认值 |
| --- | --- | --- |
| `--before` | 归档这个日期（`YYYY-MM-DD`）之前的记录 | 30 天前 |
```

README 的“用法”列表加一行：

```markdown
- `acme archive`：归档指定日期之前的记录，参数见[命令参考](docs/cli.md#archive)。
```

## 收尾汇报

- 修改的文件，以及每处修改依据的 diff 位置（文件与函数、常量或参数名）。
- 运行的检查与结果。
- 需要人工确认的项。
- CHANGELOG 需要补条目时，提示使用 release-notes。
- 项目有 `docs/adr/` 或 `docs/decisions/`，且这次改动推翻或修改了其中某条记录的决定时，提示需要一条新的决策记录。
